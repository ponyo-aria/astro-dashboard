# 進捗報告

このファイルには、各ステップで決めたことと進捗を記録する。

## 決定事項（プロジェクト全体）

- フォルダ構成：`src/screens`（画面）、`src/logic`（判定・天文計算ロジック）、`src/api`（通信）、`src/storage`（保存）、`src/config.js`（しきい値などの設定）、`tests`（テスト）、`public`（アイコンなど静的ファイル）
- GitHub Pages への公開方法：シンプルな方法（`npm run build` → `gh-pages` パッケージで公開用ブランチに反映）を採用
- GitHub のメールアドレスは非公開にし、コミットには noreply アドレスを使う（手順は Step 0 の報告に記載）
- APIキーやパスワードなどの秘密情報はコミットしない（将来必要になった場合は `.env` ＋ `.gitignore` で除外し、コミット前に必ず確認する）
- 報告書を含め、住所など個人を特定できる情報は書かない
- コミット前には `git status` の内容を一緒に確認してから進める
- 破壊的な操作（force push・ブランチ削除・公開範囲の変更など）は事前に説明し、オーナーの了承を得てから実行する

## Step 0：開発環境と土台づくり

- Vite（vanilla JavaScript）でプロジェクトの土台を作成
- 上記フォルダ構成で配置
- 「Hello」を表示する画面を作成
- Vitest を導入し、ダミーテスト1件を用意
- `npm test` が通ることを確認
- `npm run build` が通ることを確認
- GitHub リポジトリ：`ponyo-aria/astro-dashboard`（Public）を作成
- コミットのメールアドレスは GitHub の noreply アドレスをこのリポジトリのローカル設定として使用（PC全体の設定は変更していない）
- GitHub Pages は無料プランではPrivateリポジトリで使えないことが判明したため、Publicリポジトリに変更して対応（ソースコードは公開されるが、秘密情報・個人情報は含めない方針を徹底）
- `gh-pages` パッケージで `npm run deploy` → `gh-pages` ブランチに公開
- GitHub Pages の設定（Branch: `gh-pages`、フォルダ: `/`）はオーナーが画面操作

## Step 1：地点管理

- 要確認の結果：
  - Open-Meteo Elevation API（`https://api.open-meteo.com/v1/elevation?latitude=..&longitude=..`）で標高を取得できることを確認。カンマ区切りで複数地点をまとめて取得できる（例：`latitude=35.1,36.2&longitude=138.1,139.2` → `{"elevation":[847.0, 1337.0]}`）
  - 短縮URL（`maps.app.goo.gl` など）は、ブラウザ上のJavaScriptからはリダイレクト先を読み取れない（CORSの制約）。仕様書どおり、専用のエラーメッセージ「座標をコピーして貼ってください」を表示する形にした
- 初期3地点の座標は、オーナーにGoogleマップのピン長押しで取得してもらった3地点ともピンポイントの座標を使用。座標の数値そのものは `src/storage/locationsStorage.js` に保存し、このファイルを含め報告書には住所を書かない
- 作ったもの：地点の追加・編集・削除・並べ替え、座標／GoogleマップURLの貼り付け入力、標高の自動取得（手で修正可）、localStorageへの保存、JSONの書き出し・読み込み（置き換え／追加）
- 自動テスト：座標解析、保存ロジック（追加・更新・削除・並べ替え・JSON書き出し読み込み）、画面の基本操作（追加・削除・不正入力時のエラー表示）
- 短縮URLの自動展開はブラウザの仕様上できないため今回は対応せず、オーナーの運用（長押しで座標取得）でカバーする方針に決定

## Step 2：天文計算

- `astronomy-engine` を導入
- 作ったもの：夜（日没〜翌日の日の出）の範囲、天文薄明の終了・開始、月の出入り、月齢、月の高度、「暗い時間」（太陽高度-18°以下かつ月高度0°未満が連続する時間）の計算ロジック
- 精度の確認：sunrise-sunset.org のAPI（2026-01-10, 東京 35.6895, 139.6917）の日の出・日の入り・天文薄明の時刻と比較し、2分未満の誤差で一致することを確認
- 画面：地点管理画面の下に「今後7夜の暗い時間」セクションを追加し、7夜分の日没・日の出・薄明・月齢・暗い時間を表示（晴れ・曇りの判定はまだ行わない＝Step 4で対応）
- オーナーからの修正依頼：近場の地点同士では差がほぼ無いため、複数地点を並べず1地点だけ選んで表示する形に変更。初期選択は「八ヶ岳ふれあい公園（野辺山）」。地点はプルダウンで切り替え可能、選択はlocalStorageに保存。将来的にはスマホのGPSから自動選択する予定（複数地点を並べて表示する画面はStep 5で作る）
- バグ修正：実際の「今日」の日付によっては、月の出入りを探す処理が無限ループに入り、画面がいつまでも表示されない不具合があった。探索の開始地点を同じ瞬間に戻してしまっていたことが原因。直近30日分どの日付でもハングしないことを確認する自動テストを追加して再発防止
- 自動テスト：外部データとの比較、暗い時間の整合性（天文薄明の範囲を超えない等）、日付をまたぐ夜の計算、画面表示の基本動作、直近30日分のハング防止

## Step 3：予報データの取得

- 要確認5項目の結果：
  1. モデル名パラメータ：MSMは `jma_msm`（エンドポイント `/v1/jma`）、ECMWFは `ecmwf_ifs`（9km解像度の最新IFS、エンドポイント `/v1/ecmwf`）。2025年10月から無料公開されたモデル
  2. MSMでも850hPaの風（`wind_speed_850hPa`・`wind_direction_850hPa`）は取得できることを確認。一方、MSMの最大瞬間風速（`wind_gusts_10m`）は常にnull（モデルが非対応）。ECMWFでは取得できるため、瞬間風速はECMWF側の値を参考にする
  3. 複数地点の一括取得：緯度・経度をカンマ区切りで渡せば1回のリクエストでまとめて取得できることを確認（例：2地点なら10個の緯度経度ペアを1回で送信）。地点ごとに「中心＋周辺4点」をまとめて1回のリクエストで取得する実装にした
  4. 最終更新時刻：`https://api.open-meteo.com/data/{モデル名}/static/meta.json` で `last_run_initialisation_time`（初期時刻）などが取得できることを確認
  5. 無料枠の利用制限：1分600回・1時間5000回・1日10000回。このアプリの使い方（起動時・更新ボタン押下時のみ、10分以内は再取得しない、1回のリクエストに複数地点をまとめる）なら十分収まる
- 作ったもの：MSM・ECMWFの予報取得、周辺4地点（北東南西5km）の計算、モデル最終更新時刻の取得、通信失敗時のエラー表示（真っ白にしない）、10分以内は再取得しないキャッシュ
- 画面：確認用の簡易表（雲量・最終取得時刻・モデル更新時刻）を追加。正式な画面はStep 5・6で作る
- 自動テスト：周辺点の距離計算、予報取得（複数地点まとめ取得・通信エラー時）、キャッシュの新旧判定、画面のエラー表示
- 実際のOpen-Meteo APIに通信して、野辺山の実データが取得・表示できることを確認済み
- オーナー確認済み：最大瞬間風速はMSMで取得できないため、ECMWFの値を使う（Step 6で実装時に反映）
